# Backend review — integrated local portal

Last updated: 2026-11-15. This records the implemented boundary and observed local checks through migrations `20261115121732`–`20261115132410`, in addition to the M1 foundation. It is not production approval or a legal-compliance claim. The isolated complete `./portal test` run is recorded separately in QA results; authored browser tests are not counted here as executed.

## Authorisation boundary

- Supabase Auth identifies actors. Public registration is disabled by local configuration. Auth user creation provisions a profile, **no role**. Editable `user_metadata` never grants permissions.
- `profiles.active` is checked from database state on every protected read/write/RPC. Disabling a profile therefore denies data access even while an old Auth access token remains valid. Operational suspension should additionally revoke Auth sessions.
- `user_roles` and `role_permissions` are server-managed. Administrative permissions require JWT `aal2` plus active membership. A senior lecturer receives no automatic access to other people's contracts or rates.
- Every current application table in `public` enables RLS, verified against the integrated local catalogue. Grants are explicit per table or column. An authenticated client can directly edit only the specifically granted safe self-profile columns, its unverified expertise selection, its private calendar, and notification read state. Claims, roles, activation, verification, documents, messages, knowledge, customer/course management and commercial mutations use restricted RPCs or the authenticated files gateway.
- Private appointments remain owner-only, including for admins. Assigned teaching sessions and fee snapshots are visible to the assigned lecturer and scoped management as appropriate. Persisted private messages, reactions and revisions require actual current room membership; administrator status never substitutes for DM membership.
- Privileged database implementations live in the **unexposed** `private` schema, with empty `search_path`, fully qualified relations, revoked default execution, and explicit actor checks. Exposed RPC wrappers run as invoker. `complete_invitation` is service-role-only and itself invoker.

## Management attestations and suspension

`verify_lecturer_topic(user_id, topic_id, verified, valid_until)` requires fresh `qualifications.verify` permission and AAL2, an active lecturer target, and an already self-selected expertise row. It never creates expertise on a lecturer's behalf. A verification expiry must be in the future; un-verifying clears expiry. The audit stores the actor, subject/topic, previous/new state and `management_attestation` basis. This is explicitly not a claim that a certificate file has been uploaded or reviewed.

`set_user_active(user_id, active)` requires `users.manage` and AAL2. It refuses self-deactivation and deactivation of the last active admin. A transaction-wide lock serializes activation changes, so concurrent admins cannot suspend each other and both succeed. Old/new activation state is audited. Existing-session API requests immediately lose all protected data/claim access after suspension; reactivation restores the unchanged roles. Auth session revocation is an additional operational action, not silently claimed by this routine.

## Atomic claims

`claim_job(job_id, idempotency_key, terms_version)` locks the actor using a transaction advisory lock and then locks the selected job row. The server checks active lecturer role, publication/deadline, future sessions, verified required expertise valid through the last session, effective executed-contract record when required, accepted terms version, and existing assignment/private-calendar conflicts. Uniqueness permits one confirmed claim per job. A GiST exclusion constraint independently prevents overlapping allocations for the same lecturer.

The claim, all session allocations, immutable fee/currency/terms/contract reference, job status, claim event, notification and room membership commit in one transaction. Retry keys are actor-scoped; reusing a key for a different job fails. Appointments use the same actor lock, closing the concurrent appointment-versus-claim race. Error results never imply a reservation. The actor's active profile is share-locked while claiming, so suspension serialises against a claim already committing.

The commercial extension first selects the newest applicable executed-contract row and then validates active status, explicit revocation, ancestor revocation and complete interval expiry coverage. It cannot silently fall back from an expired/revoked replacement to an older active row. Registration/status changes take the same lecturer transaction lock as claiming. Agreement rows retain the exact PDF version/hash where present; previously accepted claims retain their original immutable agreement link.

Capacity is deliberately constrained to **one slot**. Cancellation/reopening/substitution needs an audited workflow before it can be enabled; management status changes refuse filled jobs. Accepted snapshots cannot be rewritten, including through ordinary service-role table updates. Service/database administrators remain trusted infrastructure actors, not adversaries defeated by RLS or application triggers.

## Private collaboration and realtime

`private.can_access_chat_room` requires a freshly active actor, a current nonremoved membership and the current role required by the room kind. DMs are canonical unique unordered pairs, created under a transaction advisory lock. Staff topic/course groups exclude participants. Participant channels reference a separate course-run relation and do not disclose commercial job/claim rows. The assigned lecturer owns their job discussion; owners manage membership through bounded, audited RPCs. DM membership has no management-edit API. General lecturer chat requires a current lecturer/senior role.

The contact directory returns safe names, IDs and role labels only. Ordinary staff discover staff; participants discover contacts from explicitly shared participant channels. Only `courses.manage` with MFA can request the minimal participant administration directory. Directory visibility never exposes biography, phone, contract files or rates from full private profiles.

Messages are persistent plain text with an 8,000-character limit, stable cursor pagination/search, sender-scoped durable retry UUIDs, 30 sends/minute, unread cursors and mute preference. Sender edits use a 15-minute window. Deletions clear current body/attachment and retain a tombstone; revisions remain under the same live room ACL. Group moderation requires membership and owner authority or `chat.moderate` with MFA. Private DM bodies are never copied into the company-wide audit log. Notifications contain IDs/kinds rather than message bodies.

Only PostgreSQL message/reaction/membership INSERT/UPDATE streams are used. Removals are tombstone updates rather than unsafe cross-room DELETE broadcasts. Membership table RLS exposes only the actor's own membership rows; the removed actor can observe their own removal marker, which authorises no content. The client waits for actual PostgreSQL replication readiness, rechecks lists and clears removed-room caches. Actual already-subscribed websocket tests establish delivery before removal and deny future rows after removal or suspension. Realtime authorization does not retract bytes already delivered to a device. Presence/typing and join-time-cached private broadcast are not claimed as implemented.

See `CHAT_SECURITY.md` for owner/invitation, idempotency and audit details.

## Private files and scanned evidence

`documents` and `document_versions` separate scoped metadata, current-version pointers, exact historical object paths and scan status/hash/version. Scope is constrained to personal, current room membership or job-before/job-after access. An owner exception does not let a removed member retain room-file access. Published-job materials-before can be read by active lecturers; materials-after require an accepted assignment or explicit job management. Participants cannot obtain commercial job files through course membership.

Personal CVs, qualification evidence, contracts and invoices use distinct management capabilities (`users.manage`, `qualifications.verify`, `contracts.read`, `finance.manage`), each subject to the current permission/MFA check. Ownership is derived or validated against a narrowly authorised target-upload operation. Senior lecturer status alone grants no private-file access. Qualification verification remains a management attestation; storing a certificate is not automatic verification or proof of legal validity.

Both Storage buckets are private. A restrictive `storage.objects` policy denies direct anonymous/authenticated access to those buckets, even if another permissive policy is added. Browser uploads/downloads go through the authenticated files Edge function. Service credentials remain server-side. The gateway validates sizes/MIME/signature metadata, reserves UUID-scoped immutable storage paths, writes quarantine, scans the stored bytes through ClamAV, and promotes only a clean verdict. Scanner errors fail closed. It records SHA-256 and the actual scanner version; limits are 10 MiB/file, 100 MiB of all version bytes per owner and ten reservations/minute per uploader. A clean scan is a scanner verdict, not a universal guarantee of safe content.

Migration `20261115132410` hardens reservations without changing the RPC signature. Reservations lock the uploader and then the quota owner in distinct advisory-lock namespaces, so two management uploads on one lecturer's behalf share the same 100 MiB limit as that lecturer's own concurrent upload. Retry UUIDs also bind creation versus replacement and the exact replacement document ID; an existing creation cannot be silently reinterpreted as a replacement or a replacement redirected to another document. Byte-for-byte retry verification belongs to the Edge file gateway in addition to these database metadata/target checks.

Binary download fetches a specific clean version, rechecks current document/membership access before fetching and before returning bytes, uses attachment disposition/sandboxed response headers and does not issue durable signed URLs. Requesting an older executed version remains possible while a replacement current version is quarantined. No permission system can revoke an already downloaded local copy. Scanner signatures, Edge secrets/origins, HTTPS, operational access and Storage/database backup/restore still need hosted acceptance.

## Knowledge and customer/course boundaries

Wiki/forum are staff-only at this checkpoint. Participant course membership does not grant knowledge access. The server accepts a closed, bounded Tiptap JSON vocabulary with safe link protocols and derives search text itself. No raw HTML, executable link protocols, images or arbitrary node attributes are accepted. UI rendering uses the same schema and treats code as literal text. Authors edit drafts with exact version checks; current and published wiki pointers are separate so a correction cannot replace the version seen by published readers. `wiki.manage` plus MFA controls publication/archive. Forum authors control their own unlocked posts; `forum.moderate` plus MFA controls pin/lock/archive/report resolution. Reports are visible only to reporter/current moderator. Deleted-post revisions remain visible only to the original author/current moderator. See `KNOWLEDGE_SECURITY.md` for exact limits and pending participant/attachment policies.

Customer identity is separate from `organisation_private_details` and `organisation_contacts`. Knowing a customer through a visible course never grants private notes/contact details; those require `organisations.manage` plus MFA. Course writes require `courses.manage` plus MFA. Lecturers see published nonarchived runs or their actual assignments. Participants see a run only through its explicit current participant-channel membership, without commercial job access. Schedule replacement is atomic and locked once jobs reference a run. Safe copies create new draft identities without copying claims, fees, users, chat membership or documents. Archives preserve history and never release accepted assignments. See `OPERATIONS.md`.

## Executed contracts, invoices and tracking payments

Contracts are externally executed PDF versions registered by `contracts.manage` with MFA for an active lecturer. The exact clean personal PDF version and SHA-256 are fixed; addenda point to a prior same-owner executed record. A lecturer's owner-only acknowledgement binds that exact hash and records **receipt acknowledgement**, not an electronic signature or a legal-enforceability assertion. Legacy fictional metadata without a PDF/hash cannot be acknowledged as an executed file.

Lecturers read only their accepted compensation, invoices and payment history unless a caller has `finance.manage` plus MFA. EUR and AUD remain separate original amounts. Invoice submission accepts at most 50 own confirmed claims in one currency and a clean owned invoice PDF. Compensation comes from immutable accepted claim snapshots, not client totals or PDF tax extraction. A unique active claim link prevents duplicate invoicing. Rejected/cancelled unpaid invoices release links; restoration must pass uniqueness again. Accepted invoice references, numbers, amounts and dates are immutable.

Finance management records approval/rejection/cancellation and original-currency partial/full payment entries. Invoice locks prevent concurrent overpayment; retry UUIDs deduplicate entries. Void-with-reason corrections retain originals and audit rather than overwrite paid amounts. Entries do not move money. No tax calculation, legal invoice review, electronic signature or banking integration is implied. Exact commercial document versions cannot be altered, and ordinary soft deletion cannot hide linked evidence. See `COMMERCIAL_SECURITY.md` for limitations, correction scope and executed tests.

## Retention, caching and operational trust

Message/post deletion is a tombstone, not physical erasure: private revisions remain intentionally retained under their specified ACLs. Wiki revisions, commercial agreements, receipts and payment corrections also retain history. File soft deletion denies ordinary reads but is not a storage purge. Linked commercial evidence is specifically protected from ordinary deletion. No completed retention schedule, subject-access/export workflow, legal-hold process or GDPR erasure guarantee is asserted. Those policies must decide when audited records and backups may be physically removed without destroying required evidence.

Browser queries are actor-scoped and cleared at access/auth changes; the PWA does not persist private application API responses, message bodies or attachment bytes in its service-worker cache. A fresh server check controls every new operation. RLS does not protect against an infrastructure operator holding database/service-role credentials, deliberate browser screenshots or a recipient retaining already delivered bytes. Least-privilege operations, credential rotation, monitoring and restore drills are separate production controls.

## Invitations

`POST /functions/v1/invite-lecturer` accepts only `email`, optional `display_name`, and UUID `idempotency_key`. It verifies Auth and then fresh database permission/MFA. It requires explicitly configured allowed origins and `PORTAL_INVITES_ENABLED=true`; the role is always lecturer. Browser code never receives service credentials.

A durable database reservation precedes email sending. Email and retry-key uniqueness prevent repeated sends, including across admins. Each actor may reserve at most five addresses per 15 minutes. The service-only completion routine assigns lecturer membership and records an audit result. An uncertain email failure is recorded and **blocked from automatic resend**. An operator must investigate failed or stuck reservations rather than editing the ledger blindly or promising delivery. Invitation sends are intentionally not automatically retried after an uncertain SMTP/network outcome.

Only local fictional mail has been authorised for testing in this work. Production/staging sending requires approved project configuration, SMTP, origins and deployment. QA verified real local Edge delivery, the captured custom Mailpit link, explicit browser acceptance, password setup, logout and subsequent new-password login. Hosted configuration still requires separate acceptance.

## Invitation link format

The SPA keeps PKCE for login and recovery. The custom bilingual invite template uses the supplied, fixed `/auth/callback` redirect plus `token_hash` and `type=invite`, rather than consuming an implicit-session fragment that the PKCE client rejects. The callback requires an explicit acceptance action and calls `verifyOtp` before password setup. Local CLI `content_path` resolves from the project workdir; local template changes require restarting Auth. Hosted projects need the invite and recovery HTML explicitly configured in the Auth email-template settings. The bilingual recovery template deliberately retains `{{ .ConfirmationURL }}` so the standard SDK PKCE challenge/verifier flow remains intact. Links and token hashes must not be copied into logs or shared artifacts; hosting should redact authentication query strings and use a no-referrer policy.

## Remaining acceptance

No hosted Supabase schema or production website was changed by these local slices. Hosted advisors and origin/secret/scanner configuration, token revocation/session policy, joint database-and-Storage backup/restore, retention/export/erasure decisions, granular permission administration, job cancellation/substitution and final load/security review remain release prerequisites. Complete participant enrolment/content ACLs, knowledge attachments, collaboration presence/ownership lifecycle and corrected legal invoice workflows remain broader product scope. E-signature and tax/banking claims are explicitly outside this implementation. Local authentication and SQL checks establish the tested boundaries only; complete desktop/mobile/PWA and production acceptance need their own evidence.
