# 2. COMPLETE CHAT & MESSAGING SYSTEM

This is a major priority.

The Luminovia Portal should offer a messaging experience comparable in convenience to established modern collaboration applications, while remaining appropriate for a relatively small professional teaching organisation.

## 2.1 Conversation types

Support:

- One-to-one direct messages
- Lecturer group chats
- General company-wide chat
- Topic-based groups
- Course-specific lecturer chats
- Separate participant/course chats
- Management groups
- Customer-specific conversations where explicitly authorised
- Private invitation-only groups
- Discoverable groups where appropriate

Do not expose internal commercial information to course participants or customers.

## 2.2 Group creation and management

Users with the relevant permissions must be able to:

- Create a group
- Enter a group name
- Add a description
- Upload a group picture
- Choose a group category
- Add searchable topic tags
- Select privacy/visibility settings
- Invite members
- Search for members
- Add multiple members
- Remove members
- Leave a group
- Rename a group
- Change its description
- Change its picture
- Change group settings
- Transfer ownership
- Assign moderators
- Revoke moderator rights
- Archive a group
- Delete a group where permitted
- View group information
- View group members
- View creation and relevant activity information
- View and manage pending invitations

Provide clear permissions for each operation.

An owner who wants to leave should be able to transfer ownership when necessary.

Deleting or archiving a course-related group must not accidentally delete the actual course, its historical allocations or legally retained business records.

## 2.3 Group membership lifecycle

Implement:

- Join a group when permitted
- Request membership when approval is required
- Accept or reject invitations
- Withdraw membership requests
- Leave voluntarily
- Remove members
- Ban or restrict members where justified
- Restore access when authorised
- Transfer ownership
- Automatically update access after assignment changes
- Revoke access after lecturer replacement or account suspension

Distinguish:

- Public/discoverable groups
- Private invitation-only groups
- System-managed course groups
- Restricted management groups

Membership changes must immediately affect server-side access to chat history and attachments according to the applicable group policy.

A user who has left or been removed must not continue receiving new private messages through a stale Realtime subscription.

## 2.4 Conversation list management

Every user should be able to:

- Pin conversations
- Unpin conversations
- Reorder pinned conversations
- Mute conversations
- Unmute conversations
- Archive conversations
- Unarchive conversations
- Hide conversations from their personal list
- Mark conversations as read
- Mark conversations as unread
- Search conversations
- Filter conversations
- Display unread message counts
- Display the last message preview
- Display the last activity timestamp
- Open a conversation directly from a user profile
- Open a relevant group directly from a course page

**Distinguish hiding a conversation for one user from deleting a conversation for everybody.**

Personal pinning, muting and archiving must not modify another user's preferences.

## 2.5 Message functionality

Messages should support:

- Plain-text content
- Multiple lines
- Links and safe link previews where feasible
- Emoji
- Reactions
- Replies to individual messages
- Optional threaded replies
- Mentions
- Copying message text
- Copying an authorised message link
- Editing messages
- Deleting messages
- Message attachments
- Message search
- Pagination and loading older messages
- Unread message indicators
- Read receipts where permitted
- Sending indicators
- Failed-message states
- Retry functionality
- Message ordering
- Automatic scroll behaviour
- Scroll-to-latest controls

Do not introduce unsafe HTML rendering or unrestricted remote embeds.

### Message timestamps

Every message must have an accurate server-authoritative creation timestamp.

Display:

- Sending time
- Creation date where relevant
- Edited indicator when modified
- Correct date separators
- User-local time zone formatting
- Appropriate DE/EN date and time formatting

Persist canonical timestamps in UTC and render them according to the user's actual time zone preference.

Never rely on the sending device's local clock as the authoritative message time.

## 2.6 Message deletion — especially important

Implement clear, separate options where permitted:

**Delete for me**
- Hide the message from the requesting user's normal conversation view.
- Do not remove it from another participant's view.
- Persist the user's personal deletion preference appropriately.

**Delete for everyone**
- The authorised sender or moderator can remove the message from normal conversation views for all participants.
- Clear its ordinary visible body and attachment references.
- Update other connected clients through Realtime.
- Show an appropriate deleted-message placeholder where the conversation policy calls for one.
- Prevent removed attachments from remaining accessible solely through that message.
- Handle users who are offline and later reconnect.

Use appropriate confirmation dialogs, permission checks and audit records.

A deletion must not be described as removing copies that were already viewed, exported, screenshotted, downloaded or retained in authorised backups.

Preserve legally required retention separately from ordinary user-visible deletion, and document the distinction transparently.

Private historical revisions must never become accessible through a blanket administrator bypass.

## 2.7 Message editing

Support editing within the existing permitted time window and rules.

Requirements:

- Original author authentication
- Server-side permission checks
- Version conflict detection
- Edited indicator
- Consistent realtime updates
- Safe retry handling
- Preservation of relevant audit history
- Correct interaction with structured mentions
- No accidental duplicate messages

## 2.8 Pinned messages and announcements

Distinguish **pinned conversations** from **pinned messages**.

Add:

- Pin an authorised message in a group
- Unpin it
- View pinned messages
- Navigate to the original message
- Display pinned-message context
- Restrict group-wide pinning to permitted roles
- Prevent stale pins from exposing deleted or inaccessible messages

Support group announcements, but reuse the existing announcement system rather than creating another independent notification implementation.

## 2.9 Attachments and uploads

Support secure sharing of:

- PDF files
- Word/Office documents
- Images
- Text files
- Teaching materials
- Other explicitly supported formats

Features:

- Upload button
- Drag and drop
- Upload progress
- File-size validation
- Multiple attachments where supported
- Safe previews
- Authorised downloads
- Filename and file-type display
- Clear scanning status
- Retry after failed upload
- Remove attachment before sending
- Access checks after member removal

Reuse the existing malware scanning, quarantine, file-versioning and permission infrastructure.

Do not bypass scanning simply to make messaging more convenient.

## 2.10 Additional chat QoL

Evaluate and implement where appropriate:

- Typing indicators
- Online/offline or last-seen status with privacy settings
- Saved messages or bookmarks
- Draft preservation
- Reply previews
- Mention autocomplete
- Search within an individual conversation
- Conversation information panels
- Keyboard shortcuts
- Message context menus
- Accessible mobile long-press alternatives
- Notification mute durations
- Group member counts
- New member system notices
- Moderation and reporting
- Blocking unwanted direct contact where compatible with operational obligations

Avoid unnecessary complexity, but ensure important user actions are not missing.
