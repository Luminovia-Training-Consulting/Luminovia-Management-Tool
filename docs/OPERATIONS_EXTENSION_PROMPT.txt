## 3. FEATURE P1 — COURSE READINESS CENTRE

Implement a fully functional course preparation and readiness management system.

### Functional requirements

Every course run must have a readiness overview that automatically evaluates:

- Lecturer assigned and confirmed
- Valid applicable lecturer agreement
- Required teaching qualifications verified
- Course materials uploaded and available
- Meeting link or physical teaching venue configured
- Customer organisation and contact information available
- Teaching dates and sessions confirmed
- Required course instructions acknowledged
- Required preparation tasks completed

The exact applicable checks must depend on the course configuration. For example, an online course requires a meeting link, while an in-person course requires a venue.

### User interface

Create a modern Course Readiness Centre containing:

- Course readiness percentage based on applicable requirements
- Status: Ready, Attention Required, Blocked, Completed
- Preparation checklist
- Responsible persons
- Missing information
- Upcoming preparation deadlines
- Direct links to incomplete requirements
- Course documents and meeting information
- Management overview across all upcoming courses

Readiness should update automatically when underlying course records change.

Do not store a manually editable readiness percentage as the authoritative status.

Provide an accessible overview, detail view and relevant dashboard widgets.

### Acceptance

A course cannot silently appear ready when mandatory information is missing.

Readiness calculations must respect document visibility, revoked qualifications and current agreement validity.

Add unit, SQL/API, integration and browser tests.

## 5. FEATURE P1 — AUTOMATIC REPLACEMENT MARKETPLACE

Extend the existing assignment lifecycle with automatic replacement opportunities.

### Functional requirements

When a confirmed lecturer cannot complete an assignment:

1. Initiate an authorised cancellation or replacement request.
2. Record the reason and affected teaching sessions.
3. Determine which lecturers are qualified and available.
4. Exclude lecturers with conflicting appointments, expired qualifications, missing contractual requirements or insufficient permissions.
5. Offer the replacement assignment to eligible lecturers.
6. Support automatic first-come-first-served claiming.
7. Immediately confirm the first valid successful claimant.
8. Notify the affected parties.
9. Transfer the necessary course access, calendar commitments and preparation information.
10. Preserve all previous allocation, cancellation and financial history.

### Replacement modes

Support:

- Open replacement marketplace
- Selected qualified lecturer invitations
- Optional waitlist or ordered notifications
- Emergency replacement marking
- Explicit management intervention where necessary

The original lecturer's confirmed assignment must not disappear prematurely. Handover and cancellation must follow a clear, authorised transition.

### Technical requirements

Use PostgreSQL transactions and locks to prevent double assignment.

A multi-day assignment must be transferred atomically when it is defined as one indivisible block.

Ensure idempotent retries, concurrent claim safety and immediate permission updates.

### Acceptance

Test at least:

- Two lecturers claiming the same replacement simultaneously
- Conflicting schedules
- Expired qualification
- Cancelled replacement offers
- Failed handover
- Partial course completion
- Concurrent original-assignment changes
- Chat/document access before and after reassignment

Draft → Submitted → Awaiting Response → Accepted / Rejected / Withdrawn → Applied

### Critical contractual behaviour

A rejected request must leave the confirmed assignment unchanged.

Applying a change must be transactional and revalidate current eligibility, schedule conflicts and resource availability.

Provide management and lecturer interfaces, notifications and version comparisons.

### Acceptance

Test changes involving conflicting dates, stale versions, changed fees, rejected amendments, concurrent approvals and already invoiced work.

## 7. FEATURE P2 — WEBSITE-TO-PORTAL INTEGRATION

Connect customer enquiries from the public Luminovia website to the existing customer-request system.

### Desired workflow

A customer visits luminovia.org and requests training.

Management can then:

- Review the enquiry

- Create or link a customer record

- Attach relevant requirements
- Assign internal responsibility
- Convert the enquiry into a course request or course run
- Track the enquiry lifecycle
- Contact the customer
- Prevent duplicate request creation

### Required implementation

Build a minimal secure integration endpoint compatible with the existing backend.

Implement:

- Input validation
- Spam and abuse protection
- Rate limiting
- Duplicate submission protection
- Safe error handling
- Appropriate origin and authentication boundaries
- Privacy notice/consent integration where applicable
- Audit and delivery status
- No leakage of internal customer data

The public Website repository is a separate project.

Inspect its actual frontend architecture before proposing changes.

Prefer preparing a dedicated website integration PR if a frontend modification is required.

**Do not merge or deploy changes to the public marketing website without explicit authorisation.**

The Portal-side intake functionality should be independently testable using fictional enquiries.

### Acceptance

Verify that a valid submission creates exactly one request, malformed requests are rejected, duplicate retries remain safe, and ordinary public visitors cannot retrieve internal customer information.
