# Production readiness: evidence and delivery backlog

This is the implementation backlog for the master directive. The [product specification](PRODUCT.md), [feature catalogue](FEATURES.md), [guide](GUIDE.md) and [API reference](../API_REFERENCE.md) remain the sources for product contracts and current features. Maintain this ledger per reviewed work package. A source finding, a test result, a published release and an authorised installation check are separate facts.

## Baseline and findings

- Source baseline: GitHub `main` at `d2fe5a29` (PR #79), with no open PRs or other remote heads observed at intake. The tracked inventory had 2,118 entries, 387 SQL migrations and 91 browser specs. The initial review mapped the principal source, API, SQL, test and deployment owners; it did not verify every permission or business flow.
- The [automatic release run](https://github.com/Luminovia-Training-Consulting/Luminovia-Management-Tool/actions/runs/45749741879) published the baseline before its [application acceptance](https://github.com/Luminovia-Training-Consulting/Luminovia-Management-Tool/actions/runs/45749741863) and [security run](https://github.com/Luminovia-Training-Consulting/Luminovia-Management-Tool/actions/runs/45749741909) were complete. The manual publisher also lacked a standalone security-run prerequisite. `P0-02` corrects both source paths; no existing release was withdrawn.
- The source includes current-account/scoped resource checks, encrypted stored chat, private file scanning and recent company/lecturer/contact restrictions. This is not comprehensive RLS or post-revocation coverage. The selfhost runbook describes password-only configuration, while `20261122013600_privileged_authenticator_policy.sql` supplies an opt-in policy. Mandatory privileged MFA, configuration consistency and recovery must be proven together before enforcement.
- The Hostinger runbooks specify a development KVM 1 and 10 GiB allocated storage with a 1 GiB owner quota, not the production sizing target. Historical native checks and encrypted backup tooling are not live proof of current off-site copies, RPO/RTO, real SMTP throughput or capacity.

## Verification record for P0-04 native restore evidence

- The full `verify-selfhost` profile installs the distribution's official `age` package and runs `deploy/hostinger/backups/test_complete_restore.mjs` before the existing native selfhost compatibility check. The fixture uses a generated fictional backup, real age encryption/decryption and owned networkless PostgreSQL containers; it never uses hosted/customer data.
- `desktop-restore-result.json` is written as a private mode-0600 atomic replacement only after decrypt, file checks, all database/role/extension checks and credentials verification pass. A wrong key is tested before first success and after an existing success; the report must respectively remain absent or byte-identical. A second successful restore must replace the previous report with the new complete measurement.
- `nativeVerificationDurationMs` measures the restore verification from before decryption/extraction through successful native verification. `backupAgeAtNativeVerificationSeconds` measures from encrypted catalog `startedAt`, a conservative lower bound on age; missing, invalid or future-dated legacy timestamps yield `null` without blocking restore.
- Local native fixture passed: 3 databases, 8 files, 3,628 ms verification and 8 seconds catalog-based backup age. The sample is informational, not a repeatable performance guarantee.
- Passed locally: 27 backup Python tests, 23 Node backup/workflow/documentation tests, Actionlint, ESLint, Prettier for changed workflow/docs and `git diff --check`.
- These are synthetic-fixture measurements, not evidence that current off-site backups exist or are fresh, that scheduled restore monitoring runs, or that an entire Auth/HTTP installation meets production RPO/RTO. Those gates remain open pending authorized external recovery and service-level acceptance.

## Verification record for P0-04 replica ciphertext/freshness check

- Added a separate read-only `--verify-replica` CLI path. It requires an exact 64-character SHA-256 pin supplied independently of the copied set, checks that the manifest bytes match before parsing, verifies declared encrypted artifacts, and requires ordered timezone-aware `startedAt`/`completedAt` values whose completion is not future-dated or older than the configured 1–48-hour limit.
- Missing/malformed pins, pin mismatch, altered ciphertext, missing declared archives, stale completion, invalid timestamps and future timestamps return a nonzero exit status. Success reports `replica_ciphertext_verified`, the exact manifest pin, observed backup age and `decryptionPerformed: false`; it does not write to the reader copy or use the VPS backup runner.
- Regression tests passed for an exact copied synthetic set, missing/wrong pins, tampering, incomplete data and stale/future/invalid freshness evidence. The complete native age/PostgreSQL fixture separately copied its fictional encrypted set, verified it against the original manifest pin, and then completed native recovery: 3 databases, 8 files, 5,693 ms native verification and 10 seconds catalog-based age.
- `python3 -m unittest discover -s deploy/hostinger/backups -p 'test_*.py'` passed all 31 tests. These are local synthetic-path results only: they do not establish an independently administered/physical store, actual recurring transfer, alerting, current off-site freshness, decryption on the replica, or production RPO/RTO. A real reader-host check and service configuration remain external acceptance gates.
