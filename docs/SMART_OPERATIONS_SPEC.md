## Delivery and communication

Hostinger Mail, with `info@luminovia.org` as the intended sender, is the selected application-email provider. Credentials belong only in private operating configuration. No supplied mailbox credential is copied to source, examples, logs or this guide. The actual server/timer/provider proof and activation state are owned by [Mail operations](NOTIFICATION_MAIL_OPERATIONS.md) and [WORKLOG](WORKLOG.md), not inferred from an email-settings form or a successful unit test.

Notifications originate from committed business events. The own inbox and operational receipts remain available independently of optional external channels. Email preferences, quiet hours and IANA zone use current identity and CAS. Private email/Push outboxes deduplicate occurrences, lease bounded work and recheck current recipient/resource/channel eligibility before dispatch. Known temporary failures have bounded retry; uncertain provider acceptance requires reconciliation rather than blind resend. SMTP acceptance alone is not proof of inbox delivery. Web Push is implemented with explicit browser/device consent, removable owner-bound subscriptions, minimal generic content and server-side provider/encryption checks. A permission-refusing headless browser or mock provider does not establish real desktop/mobile notification delivery.

Staff contact sharing is an explicit own email/phone opt-in, private by default, with current staff-only directory projections and safe actions. It creates no administrative consent override or client/participant directory grant. The separately selected course customer contact is an explicit same-organisation course setting, not a fallback to private Auth/profile data or every customer-directory contact.

## Validation and rollout boundaries

Each vertical requires real PostgreSQL permission/concurrency checks, actual Auth/REST/Storage where relevant and meaningful desktop/mobile DE/EN journeys. The earlier root-owned source checkpoint reported **499 unit/component passes**; later Teaching Day focused checks separately passed five new and nine existing SQL groups plus eleven UI/contact cases, type/lint and documentation checks. These numbers are not added together into an invented new whole-source result. Auth/API/browser cases that are authored, earlier accepted checkpoints and current focused results do not establish the pending complete merged/native/retained-data/PWA gate.

Real desktop/mobile permission, installation, notification delivery and external calendar behaviour require their actual supported environments. Mail/provider proof, a worker source file, a browser mock or a source migration inventory does not establish a running authorised timer, installed release or production/legal acceptance. [QA_RESULTS](QA_RESULTS.md), [WORKLOG](WORKLOG.md), the persistent [implementation plan](IMPLEMENTATION_PLAN.md) and feature/operations guides retain the actual tested, untested, pending and externally dependent state. The complete master scope remains required throughout.
