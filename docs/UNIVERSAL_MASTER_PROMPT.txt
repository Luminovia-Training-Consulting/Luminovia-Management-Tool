4. REQUIRED BACKEND AND DEPLOYMENT STACK
Default architecture: managed Supabase backend + static React/Vite frontend on existing compatible Hostinger web hosting. No extra Node/Express/Nest/Django service, self-hosted Supabase stack, Kubernetes, Redis or microservices unless a clearly demonstrated requirement justifies the added complexity.
- Supabase PostgreSQL is the transactional source of truth.
- Supabase Auth provides invitation-only accounts, authenticated sessions, verification, password recovery and MFA for privileged users.
- Row Level Security (RLS) and precisely scoped GRANTs enforce access in every exposed table. Never trust role or user IDs supplied by the browser for authorisation.
- Supabase Realtime provides message delivery and relevant UI updates; persist messages in PostgreSQL.
- Supabase Storage uses private-by-default buckets for course materials, chat attachments, CVs/certificates and contracts; metadata in PostgreSQL.
- PostgreSQL functions/RPC implement the atomic assignment-claim transaction. Edge Functions implement secrets-bearing operations, email integrations and privileged workflows where needed.
- Hostinger serves the production-ready static frontend at portal.luminovia.org when DNS/hosting and deployment approval are available. Separate staging and production Supabase environments. Select an appropriate EU location such as Frankfurt where available and verify contractual/privacy implications.
- GitHub as repository, Actions for CI checks and approved deployment, migrations under version control, separate environment secrets, monitoring, off-site backups and documented restore/rollback.
- Auth emails and application notifications require configured transactional SMTP/email service (Hostinger Mail or another approved provider); check deliverability and rate limits.
Security guardrails: never put Supabase service-role/secret credentials in the browser, never use user_metadata for authorisation, and do not use broad admin bypasses or unreviewed SECURITY DEFINER functions to paper over RLS issues. If privileged routines are needed, isolate, lock down execution grants and audit them. Check the current Supabase documentation/changelog before implementation.
5. FUNCTIONAL PRODUCT MODULES — ALL REQUIRED IN THE TARGET PRODUCT
A. Dashboard and global navigation
Personal greeting/brand hero, open jobs matching user expertise, upcoming assignments, unread messages, pending contract items, calendar preview, recent documents, alerts and direct shortcuts. Role-adapted content and universal permission-aware search. Admin overview includes unfilled jobs, upcoming teaching blocks, lecturer availability, outstanding documents, earnings/costs and required follow-ups. Don't expose commercially sensitive KPIs to other roles.
B. Users, authentication, detailed profiles and permissions
Invite and deactivate users; email login/recovery; optional profile avatar and biography; phone/email and visibility preferences; country/time zone/languages; CV upload; qualifications, degrees, certifications and expiry dates; teaching experience; tools, programming languages, topics; verification by management; contract status and preferred hourly/daily rates where authorised. Click profile to start a 1:1 chat. Self-service editing with admin verification for evidence and eligibility. Roles: admin, management, senior_lecturer, lecturer, participant. A user may have several roles. Use granular permissions, not a simplistic hierarchy; senior lecturer does NOT automatically see other contracts or rates. Customers are normally directory entities, not user accounts, unless later approved.
C. Topic / Tool / Programming-language catalogue
Create/edit hierarchical, searchable topics; skills, software/tools and programming languages, with aliases, DE/EN labels and related-course metadata. Lecturers select expertise on profiles; admins validate required qualifications for restricted jobs. Search/filter jobs and lecturer availability using these tags. Include Python, Java, C#, JavaScript, SQL, IT Security, Scrum, Jira, Excel, Wireshark, etc. only as examples, not an exhaustive hard-coded list.
D. Customers, employers and contact directory
Organisations with names, types, industry/topic tags, contact people, business email/phone, location/time zone, private notes, relevant files and linked course runs/jobs. Search, filter and organise customer records by name, location, topic or tags. Permissioned views: business contacts and internal notes are not automatically visible to every lecturer. Offer click-to-message/email contact actions where appropriate.
E. Course catalogue, runs and sessions
Separate reusable course_templates from actual course_runs, each with course_sessions with precise start/end instants and display time zone. Course descriptions, syllabus, topics/tools/languages, teaching mode, prerequisites, customer, venue/online links, participant groups, assigned lecturers, shared documents and course chat. Allow one course run to be divided into independently claimable jobs when multiple lecturers are needed; otherwise offer the complete multi-day block as one job. Duplicate templates/runs without duplicating unwanted contracts or personal data.
F. Jobs marketplace + Kanban + atomic first-come-first-served claims
Admins create/publish/edit/unpublish/duplicate/archive vacancies. Fields: course, employer/customer, title, description, detailed sessions (date/time from–to), IANA time zone, online/on-site, location/link, capacity, required skills and verification, eligibility rules, applicable contract terms, attached documents with pre-/post-claim visibility, offer amount + currency + rate unit (per_day, per_teaching_unit, per_hour, or fixed_total), estimated total compensation, publication/claim deadlines and statuses. Rich search/filter by topic, tools, programming language, customer, date range, duration, price/rate, status, delivery type and availability; saved filters and sorting. Offer Kanban, list, and detailed views. Admin may reorder/edit permitted statuses; lecturer must NOT be able to drag a card into 'confirmed' to bypass actual claiming.

Non-negotiable claim logic: an authenticated, eligible lecturer presses 'Claim now'; the first successfully committed database transaction wins and is immediately confirmed. No routine admin approval queue. Atomic PostgreSQL transaction/locking and uniqueness constraints guarantee one winner for one available slot, no double booking and all-or-nothing reservation of every date in a multi-day block. Validate qualifications, contract prerequisites, conflicts with existing confirmed assignments, job availability, capacity and the accepted terms/rate server-side. Preserve immutable rate/currency/terms snapshot, claim audit trail and idempotency for retries. If rejected, give a clear real-time result (filled, conflict, not eligible, prerequisite missing), never false success. Successful claims create calendar allocations, chat membership/resource permissions and notifications. Include cancellation, reopening and substitutes, with an audit trail and safeguards for accepted work. Do not silently mutate the accepted deal.
G. Personal and global calendar
Each lecturer has private editable events, availability and blocked-out dates; confirmed jobs appear automatically. Company global calendar contains only explicitly published courses/global events, not people's private appointments. Month/week/day/agenda view, timezone indicators, next/previous and date navigation, quick-add/drag or edit where appropriate, event descriptions/files/links, invitations and reminders. Correct time-zone handling across Europe/Berlin DST and Australia/Brisbane. Optional ICS exports and read-only subscription can follow the main implementation.
H. Chat and messaging
One-to-one DMs from profiles, lecturers-only general/global chat, topic/interest groups, course-specific chats, and separate course-participant channels. Message history, timestamps, unread counters, read states, typing/presence if practical, mentions, emoji reactions, edit/delete with audit policy, search, mute settings, link sharing, file/image/PDF attachments, drag/drop and upload progress. Group owner/moderator, invites/removals and permission-aware realtime. Keep course commercial lecturer discussions separate from participant-facing discussions. A standard admin must not automatically be able to read private DMs just because they have admin permissions.
I. Files, attachments and document centre
Upload PDF, Office, images and appropriately restricted archives; metadata, owner, classification, tags, folder/category, related job/course/user/chat/contract, preview, download, replace/version, rename, accessible sharing links and optional expiry. Shared course materials, job attachments and chat uploads all use consistent permission logic. Private signed URLs should be short-lived and authorisation-checked. File size/MIME allowlists, upload limits, virus/malware scanning/quarantine process for untrusted content, safe file naming, access-revocation behaviour, audit and retention. Do not cache sensitive files offline. Separate large video hosting.
J. Contracts, agreements and legal documents
Each lecturer can view/download their personal master freelance contract, addenda and assignment confirmations. Admin/authorised management see contract status, effective/expiration dates, amendments, versions, approval/acknowledgement records and renewal reminders. Link accepted job terms to the correct contract version. Store reliable version/hash and timestamped acceptance history. Do not build an unsupported claim that checkbox/signature-image uploads create a legally sufficient signature: use existing executed contracts initially and recommend a proper e-sign provider or legal review when legally required. Include privacy/legal pages and contractor-data retention policies as configurable documents.
K. Wiki and forum
Searchable multilingual category navigation, internal articles, reusable teaching materials, rich text, embedded code blocks with language labels/syntax highlighting, attachments, revision history, edit permissions, links to course templates; forum categories/threads/replies, pinned questions, accepted answers, moderator controls, report/lock/archive and subscriptions. Wiki holds authoritative knowledge; Forum holds discussions. Respect permissions and document visibility.
L. Finance and invoices
Personal earnings overview based on accepted assignments: expected, completed, invoiced, paid; downloadable statements. Admin view: client, course, contracted fee unit and currency, lecturer costs, invoices with uploaded PDFs, invoice number/due date, payment status and date, CSV export and simple reports. EUR/AUD amounts stored in original currency without hidden conversions. This is invoice/compensation tracking, not a payroll, accounting, tax engine or banking integration.
M. Notifications and announcements
In-app inbox and unread counts; new matching jobs, claims, cancellations, chat mentions, changes, new assignments, contract reminders, upcoming sessions. Email notifications and configurable per-user preferences/quiet hours. Initial PWA need not support web push on every platform; implement web push later with honest platform capabilities. Notifications must be sent only for committed events; ensure retries do not send duplicate announcements. Avoid sending secrets or sensitive document text in email or push bodies.
N. Administration
User invites, suspensions, roles/permissions, qualification verification, customer and contact records, course templates/runs/sessions, job publishing, document organisation, wiki moderation, chat/group moderation under disclosed policy, contracts, invoicing, reporting, global announcement banners, taxonomy management, brand/notification settings, DE/EN content, audit events, CSV export, retention controls, backups and diagnostic/status pages. Support reliable bulk operations and recoverable mistakes, not irreversible destructive actions without confirmation.

7. SECURITY, RELIABILITY, PRIVACY AND QUALITY BARS
- Require login before private routes. Granular permission enforcement at DB/API layer; RLS on every exposed Supabase table and private storage. Privileged admin claims should be reviewed and logged. Least privilege, MFA for admins, secure session handling and explicit revocation.
- Protect contracts, CVs, qualifications, invoices, private calendar entries, messages and customer details from horizontal access (forged IDs, guessed storage paths, direct API queries, altered claims and modified JWT/user metadata).
- Use standard web protections: form validation, HTML sanitisation, safe URL handling, anti-spam/rate limiting, Content Security Policy where compatible, dependency scanning, secure secrets and no credentials in Git or browser bundles.
- Calendar times should be stored as canonical instants with the intended time zone preserved; display local times correctly and document ambiguities around DST.
- Accessibility target WCAG 2.2 AA; responsive layouts and keyboard accessibility throughout; meaningful focus, loading, error and empty states.
- PWA is installable on supported desktop and mobile browsers over HTTPS with a manifest, correct icons, service worker, update handling and offline fallback. Claiming jobs, sending messages and file uploads must require online server confirmation. Never cache private sensitive data indiscriminately.
- Monitoring, structured error logs, backups of PostgreSQL and actual Storage file objects, restore drills and a tested rollback. Database backup alone does not back up uploaded Supabase Storage file binaries.
- Privacy/GDPR: identify lawful purposes, access/retention/deletion, DPAs and processor locations, limited exposure to course participants. Do not assert legal compliance or e-signature enforceability without a legal review.
8. VALIDATION: WHAT 'FUNCTIONING' MEANS
Test representative user journeys in a real browser and at the data/API layer:
1. Admin invites lecturer; lecturer signs in, edits bilingual profile, adds expertise and uploads a permitted certificate. Unauthorised user cannot access private files.
2. Admin creates customer, course template, five sessions, job with tags/rate/attachments and publishes; eligible lecturer finds it via multiple combined filters and sees correct amount and localised times.
3. Run 50 parallel claim attempts against one single-slot job: exactly one successful claimant, no partial multi-day allocation and no duplicate notifications; duplicate requests from winner are idempotent. Calendar and job status reflect the committed result. Ineligible/contract-expired/conflicted lecturer cannot claim.
4. Lecturer adds private calendar appointment; another lecturer cannot see it. Global event is visible only according to publication rules. Berlin/Brisbane and DST tested.
5. Lecturer sends private message, course group message and attachment; participants see only permitted chat and files; removing a member removes access, including to storage and realtime channels.
6. Admin/lecturer can upload/download/preview authorised course materials; neither can use a guessed URL to see another lecturer’s contract or invoice.
7. Wiki article and forum thread can be created, searched, edited and moderated according to role; code blocks preserve syntax text safely.
8. Fees and currency snapshots remain unchanged after admin edits a job template; invoice workflow and exports match authorised records.
9. Complete DE/EN and light/dark/system checks on desktop and mobile. Install PWA on supported platforms; verify offline/no-connection error state and absence of leaked sensitive cache.
10. Run unit/component/E2E tests, migration tests, SQL/RLS tests, lint/typecheck/build, accessibility tests and backend permission/adversarial tests. Record actual commands and results; fix errors. Do not mark untested functionality as complete.
