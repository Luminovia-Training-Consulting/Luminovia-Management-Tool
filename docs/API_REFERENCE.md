# Luminovia platform API reference

The account facade and native domain RPCs use the same Supabase Auth identity and current database permissions. Granular administrative mutations require verified AAL2. Client memberships, private rooms/files, accepted rates and reviewer eligibility are checked server-side. A browser-visible role flag never grants access.

## Authentication and account lifecycle

Use Supabase Auth for password login, recovery, password/email changes, sessions and TOTP. Public signup is disabled. Auth URLs use the configured project base URL and public apikey; authenticated calls use the user's bearer JWT. Never distribute service-role credentials.

The versioned account facade is /functions/v1/accounts/v1 with its machine-readable OpenAPI at /functions/v1/accounts/openapi.json. Supported resources:

| Method     | Path                                       | Purpose                                                  |
| ---------- | ------------------------------------------ | -------------------------------------------------------- |
| GET/PATCH  | /me                                        | Own identity/roles/capabilities and safe profile editing |
| GET        | /users?q=&limit=&offset=                   | Administrative bounded account search                    |
| GET        | /roles                                     | Role/capability catalogue                                |
| PUT        | /users/{id}/roles                          | Audited multiple-role assignment                         |
| PATCH      | /users/{id}/status                         | Reversible suspension/reactivation                       |
| PUT/DELETE | /users/{id}/organisations/{organisationId} | Scoped client access/revocation                          |
| POST       | /invitations                               | Reserved/idempotent role-bound invitation                |

Browser Origins are allowlisted; authenticated CLI clients can omit Origin. Bearer authentication remains required for account data. Errors return safe error codes and proper status; failed/uncertain writes are not reported as success. Self/equal/higher/last-admin protection spans role and status changes. Role entries carry assignable and account entries carry can_assign_roles/can_change_active; company financial membership grants remain administrative. Invitation timeout retains its ledger for reconciliation and never automatically resends.

## Native domain operations

Use POST /rest/v1/rpc/{function} with JSON argument names shown below, the public apikey and the same bearer JWT, or supabase.rpc(function,args). Read-only tables are also available through the Data API with their explicit grants/RLS. Server-only completion functions are unavailable to authenticated clients. The legacy invite-lecturer endpoint and reserve/complete wrappers share the new ledger for compatibility; new multi-role integrations use the account API.

Client requests and new commission jobs use gross_amount/gross_total_amount. Legacy create_job remains a net-compensation compatibility operation; it does not fabricate unknown customer revenue. Role-priced offers store zero sentinels in raw jobs price columns. Use job_offers() for the current actor-specific quote and its terms_version; Management receives null protected prices. Accepted claims and invoices contain immutable net compensation. Only admin/owner gross capabilities and own-organisation client projections expose relevant gross values. Money stays in original currency. configure_compensation_policy and commission_offer_policy require current Administration MFA; no real policy defaults are committed in this public source. Policy changes apply to future offers and captured offer rates remain private. Personal welcome progress RPCs accept no target user ID. Payment RPCs record tracking entries, not bank transfers.

Profiles/reviews/labels/avatars, courses/enrolment/source provenance, resource comments, jobs/claims/calendar, chats/wiki/forum, contracts/invoices/payments and client/revenue operations are included in this generated inventory. Use the feature security documents for exact resource eligibility.

## Course source revisions and staff comments

course_run_job_defaults returns the trusted source_revision, content/customer IDs and exact session references for an existing run. create_course_run_job accepts only financial/terms/status fields plus the reviewed source_revision and request identity; it locks the existing source and rejects stale previews or duplicate active offers. Staff comments use their own resource ACL, cursor/version and idempotency parameters. Client and learner access does not grant teaching-discussion access. See COURSE_BUILDING_BLOCKS.md and RESOURCE_COMMENTS.md.

## Files and API consistency

The files Edge Function accepts bounded multipart uploads and authenticated exact-version downloads. Quarantine/actual scanning precedes clean availability; clients cannot bypass the gateway by guessing Storage paths or signing URLs. Profile images additionally use a selected exact clean canonical PNG via the same gateway action=avatar/user_id. profile_avatar exposes only permitted selection metadata; set_profile_avatar selects an owned clean avatar or removes it. The gateway rechecks visibility/selection after fetching Storage bytes; general personal-file access is unchanged. See PROFILE_AVATARS.md for upload constraints and revocation. No private resource is cached offline.
